# Forge 0.10.0

Released 2026-10-09. The full list of changes is in
[CHANGELOG.md](../../CHANGELOG.md#0100---2026-10-09). This page summarizes
it for users and lists what may need attention when upgrading from 0.9.0.

## Highlights

### Servers run on the bytecode VM

`@server` programs no longer fall back to the tree-walking interpreter. The
VM runs the top level once, freezes the result into a read-only template and
forks a private VM per request (and once per WebSocket connection), with the
same isolation guarantees as before: a handler's changes to globals,
collections or captured closure state never reach other requests. CPU-bound
handlers get the VM's speed. On one loaded 4-core machine, `fib(25)` per
request went from 5 to 1,030 req/s and `/ping` from 4.6k to 12.8k req/s.
`--interp` still serves on the interpreter. Decorators the VM cannot honor
keep the program on the interpreter.

### Resource limits for untrusted code

- `--max-fuel <n>` is a deterministic step budget: a run stops at exactly
  the same step every time.
- `--max-memory <bytes|K|M|G>` caps memory.
- Caps on open files, sockets, subprocesses, tasks, string and collection
  sizes, and imports are checked before allocating, so
  `repeat_str("x", 1e12)` fails fast instead of taking down the host.

The same limits are available to embedders through `Sandbox::max_fuel`,
`Sandbox::max_memory` and `forge_lang::Limits`, and to Python through
`Sandbox(max_fuel=..., max_memory=...)`. `forge mcp` applies them to every
`run_forge` call by default: 400M VM instructions (200M steps with
`--engine interp`) and 256 MiB.

### Sandboxed code runs on the bytecode VM

`Sandbox`, `forge mcp` (`run_forge` and `@tool` calls) and the Python
`Sandbox` now run untrusted code on the VM by default, under exactly the
same containment as the interpreter: deny-all permissions, a fresh
fuel/memory/handle budget, captured and capped output (including from
spawned tasks), deadlines and cancellation that reach blocking waits, and
unawaited tasks stopped when the run ends. Every sandbox, MCP and security
regression test runs on both engines. Choose the engine with
`Sandbox::engine(Engine::Interpreter)`, `forge mcp --engine interp` or
`Sandbox(engine="interp")`. `run_forge` sessions still use the
interpreter.

### Forge in more places

- **Python package** (`bindings/python`, published to PyPI as
  `forge-lang`): `forge_lang.Sandbox` runs untrusted Forge code in-process
  under the deny-by-default sandbox. It releases the GIL while running and
  raises typed exceptions that carry the stable error `code` and a `hint`.
- **Browser playground** (`docs/playground/`): the language core compiled to
  WebAssembly. It has an editor with inline type-checker diagnostics, share
  links, the browser-safe examples and a 15-lesson guided tour. Programs
  run in a Web Worker with a fuel and memory budget. Features that need an
  operating system report that they are not available in the browser.
- **Native plugins**: `import native "path/libfoo"` calls Rust or C
  functions through a versioned C ABI. The SDK is the `forge-plugin` crate,
  with `#[forge_fn]` and `export!`.

### A real type checker, with stable error codes

- **Inference and diagnostics.** The checker infers local types and checks
  them against declared types and the engines' own run-time rules. It
  reports unknown names, fields and members with "did you mean"
  suggestions, wrong argument counts, invalid operators, missing returns,
  unreachable code and non-exhaustive `match`. Each diagnostic has a stable
  code (`T0001`-`T0018`).
- **Runtime errors.** Every runtime and syntax error has a code
  (`E0000`-`E0033`) shared by both engines. `forge explain <CODE>` explains
  any code.
- **Tooling.** `forge check [--format json]` type-checks without running,
  and `--error-format json` prints every diagnostic as one JSON line.
- **`--strict`** makes type diagnostics errors and checks annotated
  arguments and return values at run time.
- **LSP.** The language server gains hover types, cross-file
  go-to-definition and references, rename, quick fixes, semantic tokens and
  inlay hints.

### MCP 2.0

- `forge mcp serve tools.fg` serves Forge functions annotated with
  `@tool(...)` as MCP tools, with JSON Schemas derived from their parameter
  types, and `@resource(...)` functions as resources.
- `run_forge` takes an optional `session_id` that keeps state between
  calls; `reset_session` forgets it.

### Packages

`forge add`, `install` and `update` resolve packages from a Git-hosted
sparse index. Every archive is checked against a mandatory SHA-256, and
packages can carry optional ed25519 signatures whose publisher keys are
pinned on first use. `forge publish --registry` and `forge yank` prepare
index changes for review.

### Performance

- **JIT Float tier.** Float and mixed Int/Float functions now compile. On
  the benchmarks, `mandelbrot` went from 0.55 s to 0.03 s and
  `spectral_norm` from 0.41 s to 0.18 s.
- **JIT calls.** Compiled functions call each other natively.
- **Counting loops.** `repeat n times` and `for i in range(..)` no longer
  build the range array.
- **Indexed globals.** Functions, builtins and modules are looked up by
  slot instead of by name: calls through globals are about 13% faster and
  code using captured top-level variables about 19% faster.
- **Benchmark gate.** Pull requests fail when a benchmark is more than 15%
  slower than the base (`tools/bench.sh`, `tools/bench_compare.py`).

### Hardening

- **Sandbox audit.** The fixable findings of the sandbox audit
  (`docs/SECURITY_AUDIT.md`, SEC-01 to SEC-16) are fixed, and each fix has
  a regression test in `tests/security/`. The audit lists the accepted
  residual risks.
- **Verified bytecode.** A verifier checks every bytecode file before it
  runs, and the bytecode loader rejects malformed input instead of
  panicking.
- **Fuzzing.** Fuzz targets cover the parser, the compiler, the bytecode
  loader and a differential VM/interpreter comparison.
- **Memory leaks.** The interpreter no longer leaks memory through closure
  reference cycles.
- **Windows.** Shell builtins work without a POSIX `sh`, and `which`
  honors `PATHEXT`.

## Upgrade notes

Most programs run unchanged. These changes can affect existing code or
tooling:

- **Embedders: `Sandbox` defaults to the VM.** Programs the VM cannot run
  faithfully still fall back to the interpreter inside the same sandbox.
  `Sandbox::engine(Engine::Interpreter)` restores the old behaviour. VM fuel
  counts instructions (about 2x interpreter steps), so revisit explicit
  `max_fuel` values.
- **`--strict` rejects a Float where an Int is declared.** A `Float` value
  is no longer accepted for an `Int` annotation; an `Int` still widens to
  `Float`. By default the type checker warns (`T0002`) and the program
  runs. Under `--strict` it is an error before the program starts, and a
  run-time check catches values the checker cannot see
  (`type error: argument 'n' of 'f' must be Int, got Float`). Convert
  explicitly with `int(x)`.
- **`which()` needs the `run` capability.** It starts a subprocess, so
  `forge run` requires `--allow-run` for it, as for `sh` and `run_command`.
  The REPL and `-e` allow it as before.
- **Native code is opt-in (`ffi`).** `import native` needs `--allow-ffi`
  (or `allow-ffi` in `forge.toml`) for `forge run`/`forge test`. It is
  allowed in the REPL and `-e`, and denied under `--sandbox`, in
  `forge mcp` and in embedded sandboxes unless granted.
- **Limit errors cannot be caught.** Running out of fuel or memory ends the
  run. `try`/`catch`, `safe` and `retry` do not intercept it, and the trip
  stays set, so a builtin that swallows it cannot resume the program.
- **Under the VM (the default engine), `spawn` copies captured state.**
  Each task gets copies of globals and captured variables, so writes inside
  a task are not visible to the parent or to other tasks. On `--interp`
  they are shared, and simple updates such as `count = count + 1` are now
  atomic. Return values from `spawn` (the `squad` result array, `await`) or
  use channels, rather than mutating captured state.
- **Sandbox policy in more places.** Under a restricted policy,
  `term.confirm`/`term.menu` and `io.args*` need `process`, `watch` and
  `path.resolve`/`path.relative` need `fs.read`, `pg.connect`/
  `mysql.connect` need `net` for the server, and SQLite `ATTACH` or `file:`
  URIs outside the filesystem grant are refused.
- **Error output.** Runtime errors print as `[E0009] Error: ...` with the
  hint shown as `Help:`. Tools that parse the old text should switch to
  `--error-format json`. A caught error's `e.code` holds the code.
  `e.type` of a caught `modulo by zero` is `ArithmeticError` on both
  engines.
- **Equality across types.** `==` and `!=` between values of different
  types return `false` on both engines. Before, this was an error on the
  interpreter. Numbers compare numerically inside collections:
  `[1] == [1.0]` is `true`.
- **Default registry.** The default package registry is now
  `humancto/forge-registry`.
- **Server handler policy.** Handlers run under the capability policy that
  was in force when the server started.

## Install

Homebrew (macOS and Linux):

```bash
brew install humancto/tap/forge
```

Installer script (Linux and macOS, verifies the SHA-256 of the download):

```bash
curl -fsSL https://raw.githubusercontent.com/humancto/forge-lang/main/install.sh | sh -s -- v0.10.0
```

From crates.io:

```bash
cargo install forge-lang --version 0.10.0
```

Prebuilt archives for Linux (x86_64, aarch64), macOS (Apple Silicon,
Intel) and Windows (x86_64) are attached to the
[GitHub release](https://github.com/humancto/forge-lang/releases/tag/v0.10.0)
with `SHA256SUMS.txt`. Each Unix archive includes `libforge_lang.a`, so
`forge build --native` and `--aot` produce standalone executables.

Python:

```bash
pip install forge-lang
```

Check the installation:

```bash
forge version    # Forge v0.10.0
```
