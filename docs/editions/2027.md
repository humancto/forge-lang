# Edition 2027 (in development)

Opt in with `edition = "2027"` under `[project]` in `forge.toml`, or
`forge --edition 2027 run app.fg`. Edition 2026 code is unaffected.
Design and rationale: [RFC 0008](../../rfcs/0008-edition-2027.md).
`forge fix --edition 2027` migrates code (see [Migrating](#migrating)).

Edition 2027 is a **preview**: its rules may still change until it is
announced stable.

### Strict `+`: no implicit conversion to String

**What changed.** In edition 2026, `+` with a String on one side and any
other value on the other converts that value to text: `"a" + 1` is `"a1"`,
`"total: " + null` is `"total: null"`. In edition 2027, `+` concatenates only
two Strings; a String and a non-String is an error. Numbers still add as
numbers, and every other operator is unchanged (`"a" * 2` and `"a" < 1`
were already errors; `==` across types stays a plain `false`).

**The error.** At run time, on both engines, `E0034`: `cannot add String
and Int` (the message names both operand types, left first), with the hint
`+ does not convert to String implicitly (edition 2027); convert with
str(x), or interpolate: "{x}"`. `catch e` sees `e.code == "E0034"`.

When the checker can see both types (`println("n=" + 1)`), the program does
not start: `T0005 operator '+' cannot be applied to String and Int`, an
error in edition 2027 even without `--strict`.

**Migration.** Use interpolation or an explicit conversion:

```forge
let n = 3
println("items: {n}")          // was: "items: " + n
println("items: " + str(n))    // also fine
```

A `.fgc` file keeps the edition it was compiled under: compiled with
`--edition 2027` it rejects mixed `+` wherever it runs, and a file from
before editions (format < 1.4) runs as edition 2026.

**Tests.** `tests/edition2027/strict_concat_test.fg` (2027, both engines),
`tests/string_concat_2026_test.fg` (2026 pin), `tests/errors/E0034_*.fg`,
`edition_2027_strict_string_concat` in `tests/error_codes.rs` (type error,
`.fgc` editions), sandbox and HTTP-fork tests in `src/sandbox.rs` and
`src/vm/serve_tests.rs`.

Code in this repository that relies on the 2026 conversion (to rewrite
with `forge fix`): `tests/parity/supported/string_ordering.fg` (`"n" + 1`),
`tests/safety_test.fg` (`1 + "x"` inside `safe`, expected to fail anyway).
### One syntax

Edition 2027 has one way to write each thing. The natural-syntax forms of
edition 2026 are removed: each is a syntax error **E0035** whose hint names
the exact replacement, and its word is no longer a keyword (`set`, `check`,
`hold`, `safe`, ... are ordinary names in 2027: `let set = 1` works).

| Removed (2026) | Write instead (2027) | Error |
|---|---|---|
| `set x to v` | `let x = v` | E0035 |
| `set mut x to v` | `let mut x = v` | E0035 |
| `change x to v` | `x = v` | E0035 |
| `define f(a) { }` | `fn f(a) { }` | E0035 |
| `forge f() { }` / `forge fn f() { }` | `async fn f() { }` | E0035 |
| `otherwise { }`, `nah { }` (also `otherwise ->` in `when`) | `else { }` (`else ->`) | E0035 |
| `hold expr` | `await expr` | E0035 |
| `emit value` | `yield value` | E0035 |
| `grab r from url` / `grab r from url with opts` | `let r = fetch(url)` / `let r = fetch(url, opts)` | E0035 |
| `repeat n times { }` | `for _ in range(n) { }` | E0035 |
| `unpack {a, b} from obj` | `let {a, b} = obj` | E0035 |
| `unpack [x, ...rest] from arr` | `let [x, ...rest] = arr` | E0035 |
| `unpack (a, b) from t` | `let (a, b) = t` | E0035 |
| `safe { ... }` | `try { ... } catch e { }` | E0035 |
| `must expr` | `unwrap(expr)` | E0035 |
| `check x` | `assert(x)` | E0035 |
| `check x is not empty` | `assert(len(x) > 0)` | E0035 |
| `check x between lo and hi` | `assert(x >= lo && x <= hi)` | E0035 |
| `say x` | `println(x)` | E0035 |
| `yell x` | `println(upper(str(x)))` | E0035 |
| `whisper x` | `println(lower(str(x)))` | E0035 |

The builtins below are removed: in 2027 they are not defined, so a use is
an unknown name — **T0006** from the type checker, **E0003** at run time —
whose hint names the replacement.

| Removed builtin | Write instead |
|---|---|
| `say(x)`, `yell(x)`, `whisper(x)` | `println(x)`, `println(upper(str(x)))`, `println(lower(str(x)))` |
| `sus(x)` | `println(x)` (sus printed to stderr and returned `x`) |
| `bruh(msg)` | `assert(false, msg)` |
| `bet(cond, msg)` | `assert(cond, msg)` |
| `no_cap(a, b)` | `assert_eq(a, b)` |
| `ick(cond, msg)` | `assert(!cond, msg)` |
| `ghost(f)` | `f()` |
| `cook(f)` | `f()`, timed with `time.now()` if needed |
| `yolo(f)` | `try { f() } catch e { }` |
| `slay(f, n)` | a loop timing `f()` with `time.now()` |

Kept in every edition: `println`/`print`, `fn`, `else`, `async`/`await`,
`yield`, `for x in range(n)`, `try`/`catch`, `Result`/`?`/`unwrap`,
`assert*`, `when`, `retry`, `timeout`, `schedule`, `watch`, `wait`, `ask`,
`download`, `crawl`, decorators — and the natural type-definition words
(`thing`, `power`, `give`, `craft`), which RFC 0008 does not remove.

New in **all** editions (additive, so not gated): the natural, query and
innovation words (`order`, `from`, `to`, `limit`, `where`, `select`, `safe`,
`check`, `emit`, `times`, `wait`, ...) are *soft keywords* — keywords only
where their construct can start, ordinary names elsewhere (`let order = 1`,
`fn safe(x) { }`, `{ limit: 5 }`); in 2027 the removed ones are not
keywords at all. Only the core words (`let`, `fn`, `if`, `for`, `in`,
`match`, `try`, `await`, ...) and type names stay reserved.

Also new in all editions: `let` destructures
objects and arrays, like `unpack` did, with renaming and `let mut`:

```forge
let {a, b: renamed} = { a: 1, b: 2 }
let [first, ...rest] = [1, 2, 3]
let mut [x, y] = [1, 2]
```

Missing fields and items bind `null`. A `let` pattern binds immutable names
unless it is `let mut`. (`unpack` binds immutable names on both engines;
before this change the interpreter alone made them mutable.)

**Replacements that are not exactly equivalent.** `forge fix` uses them
anyway; review these when a program relied on the difference:

- `must e` passed a plain non-null value through and failed on `null`;
  `unwrap(e)` accepts only a `Result` or an `Option`. Error messages differ
  (`must failed: ...` vs `unwrap() on Err: ...`).
- `check` failed with E0022 `check failed: ...`; `assert` fails with E0021
  `assertion failed: ...`. `check x is not empty` passed for any value that
  is not an empty string, an empty array or `null` (so `5` and `{}`
  passed); `len(x) > 0` fails for `{}` and is an error for numbers.
- `safe { }` as the last statement of a function made the function return
  the block's value; `try { } catch _ { }` does not. `forge fix` reports
  `safe { }` used as a value instead of rewriting it.
- `bruh`, `bet`, `no_cap`, `ick` raised `BRUH: ...` (E0025), `LOST THE BET:
  ...`, `CAP DETECTED: ...`, `ICK: ...`; the `assert*` replacements raise
  E0021 with their own wording. `bet`/`ick` treated a non-Bool condition as
  `true`; `assert` uses truthiness.

Tests: `tests/edition_one_syntax.rs` (every form and builtin, both engines,
both editions), `tests/edition2027/one_syntax_test.fg`,
`tests/errors/E0035_removed_syntax.fg`.

### Annotations are enforced

**What changes.** In edition 2026 every type-checker diagnostic is a
warning unless you pass `--strict`, so a wrong annotation is only a
hint:

```forge
fn f(xs: [Int]) -> Int { return xs[0] }
say f(["a"])        // 2026: warning T0002, prints "a"
```

In edition 2027:

1. A diagnostic that contradicts something the program **declared** is an
   error, and nothing runs (no partial output). This applies to
   `forge run`, `forge test` (the file fails, its tests do not run),
   `forge -e`, the REPL (the input is rejected), `forge check`, the
   embedding `Sandbox` (`SandboxError::Type`, kind `"type"`) and
   `forge mcp` (`run_forge` returns `error.kind = "type"` with
   `error.diagnostics[]`, each `severity: "error"`; `check_forge` reports
   them with `severity: "error"`). Errors render exactly like `--strict`
   errors, with a closing `type checking failed with N errors (edition
   2027: declared types are enforced)`.
2. Annotated function and lambda arguments and declared return values are
   checked **at run time** on every call, on both engines — the `--strict`
   instrumentation, now on by default for annotated code:
   `type error: argument 'n' of 'double' must be Int, got String` (E0017).
   Values the checker cannot see (JSON, results of unannotated functions)
   are caught at the boundary instead of far away. Unannotated functions
   are not instrumented and cost nothing. Imported modules get the same
   treatment when they are loaded: a declared-type contradiction refuses
   the import (`import 'm.fg' type error: m.fg:1: [T0003] ...`), and the
   module's annotated functions are checked at run time.
3. Generic type parameters must agree within a call. Statically,
   `fn pair<T>(a: T, b: T)` called as `pair(1, "x")` is T0002, and
   `fn first<T>(xs: [T]) -> T` called with `[Int]` returns `Int`; a call
   that passes both Int and Float makes `T` Float. At run time, a
   parameter declared exactly `T` binds `T` from the arguments of each
   call (`type error: argument 'b' of 'pair' must be Int like argument 'a'
   (type parameter T), got String`) and a `-> T` result is checked against
   that binding. A type parameter that only appears inside another type
   (`[T]`, `Box<T>`, `?T`) is checked statically only; struct generics
   (`struct Box<T> { value: T }`) are checked statically
   (`let b: Box<Int> = Box { value: "s" }` is T0001).
4. A declared `Float` makes an Int a Float. The checker accepts an Int
   where `Float` is declared, and at run time the value is converted, so
   arithmetic written against a Float never silently becomes integer
   arithmetic: `fn half(x: Float) -> Float { return x / 2 }` gives
   `half(3) == 1.5` (it was `1`), `fn f(n) -> Float { return n }` returns
   `2.0` for `2`, `let y: Float = 7` binds `7.0`, and a struct field
   declared `Float` (`Price { amount: 5 }`, or a default `= 0`) stores a
   Float. Nested positions convert too (`[Float]`, `?Float`, tuples, map
   values, `Result<Float, E>`); an Int that a union member accepts as it
   is stays an Int (`type Num = Int | Float`), and `Set<Float>` elements
   and map keys are left alone. The rule is `semantics::types::widen`,
   applied by the `__types.check` instrumentation (and `__types.widen` for
   `let`s and struct fields, which are still only checked statically) on
   both engines and in JIT-compiled code. Edition 2026 without `--strict`
   runs no instrumentation and never converts: write `float(x)` there.
   Struct literals of a struct declared in another module are not
   converted (the instrumentation sees the declarations of its own file).
   A whole Float prints without decimals (`println(1.0)` prints `1`), so
   the difference shows in arithmetic and `typeof`, not in `str()`.
5. Diagnostics that rest on *inferred* types or on engine rules stay
   warnings — gradual code is never rejected for what the checker guessed.
   `--strict` still makes every diagnostic an error (and is the stricter
   mode in both editions).

**Which codes become errors** (`Code::contradicts_declaration`):

| Code | Diagnostic | 2026 | 2027 | Why |
|---|---|---|---|---|
| T0001 | value does not match a declared variable / field / default type | warning | **error** | contradicts a declaration (except an `unwrap_or` fallback against an inferred `Option`: warning) |
| T0002 | argument does not match the parameter's declared type | warning | **error** | contradicts a declaration (generic parameters included) |
| T0003 | returned value does not match the declared return type | warning | **error** | contradicts a declaration |
| T0012 | type does not provide what an interface requires | warning | **error** | contradicts the `give ... the power` declaration (a method's *inferred* return type that does not match: warning) |
| T0015 | annotation names an unknown type | warning | **error** | the annotation cannot be enforced |
| T0016 | struct literal leaves out a field without default | warning | **error** | contradicts the struct declaration |
| T0020 | import not found (or unreadable) | warning | **error** | the program declared a module that is not there; running fails at the import anyway (E0019) |
| T0021 | `import { P as Q }` renames a struct, type, variant or interface | warning | **error** | only functions and variables can be renamed; running fails at the import anyway (E0019) |
| T0004 | wrong number of arguments | warning | warning | engine rule (E0005 at run time) |
| T0005 | operator on unsupported types | warning | warning | engine rule, often on inferred types (see strict operators) |
| T0006 | unknown name | warning | warning | engine rule (E0003 at run time) |
| T0007 | unknown struct field / method | warning | warning | rests on the object's inferred struct type |
| T0008 | unknown module member | warning | warning | engine rule |
| T0009 | missing return | warning | warning | flow analysis is conservative; falling off the end of `-> T` is caught by the run-time return check |
| T0010 | unreachable code | warning | warning | style |
| T0011 | non-exhaustive match | warning | warning | engine rule (E0026 at run time) |
| T0013 | call of a non-function | warning | warning | engine rule (E0004) |
| T0014 | Option used as its value | warning | warning | rests on inferred types |
| T0017 | assignment to immutable binding | warning | warning | engine rule (E0006) |
| T0018 | name used before its definition | warning | warning | engine rule |
| T0019 | result of `push(xs, v)` discarded | — | **error** | edition rule: in 2026 the statement appends to `xs`, so it is not reported there |

`--strict` makes every row an error in both editions (T0019 is reported in 2027 only).

**Cost.** Unannotated programs run the same program as in 2026 (pinned by
`typechecker::corpus_tests::unannotated_benchmarks_are_not_instrumented_in_2027`
over the `tools/bench.sh` workloads). For annotated code: the JIT
compiles a check whose value provably fits as the identity, so
`fn fib(n: Int) -> Int` runs at unannotated speed on the VM; a scalar
check costs ~1.3x on a loop that does nothing but call a two-argument
annotated function (both engines); a binding of a generic parameter
costs ~1.2–1.9x on such a loop; and collection annotations are checked
element by element, so `xs: [Int]` costs O(len) per call (an O(1)
function taking a 1000-element `[Int]` runs ~3x slower on the
interpreter and ~9x on the VM). Annotate collections as `[Any]` (or leave
them unannotated) on hot paths that take large arrays.

**Not covered.** Annotated `let` bindings are checked statically only
(as under `--strict`; a declared Float still converts an Int, see 4); imported modules are checked when they are run,
not by the importer (and a `Sandbox` does not read imported files while
checking). The REPL checks each input on its own: a call of a function
defined in an earlier input is checked at run time only.

**Migrate.** Fix each error (the message and `forge explain <code>` say
how), or loosen the annotation to what the code really accepts. The
repository's corpus (tests, examples, parity fixtures) has no 2027 type
errors and runs identically under both editions.

**Tests.** `src/typechecker/tests.rs` (`edition_2027_*`, every code under
both editions, generics), `tests/edition2027/annotations_test.fg` (run-time
checks on both engines), `tests/edition2027_annotations.rs` (CLI: run,
`-e`, `check`, `test`, `--strict`; 2026 warns and runs),
`sandbox::tests::edition_2027_*`, `mcp::tests::edition_2027_*`,
`vm::jit_tests::jit_*annotation_checks*`.

### `push` is a pure function

**What changed.** In edition 2026, `push(xs, v)` returns `xs` with `v`
appended **and**, when `xs` is a mutable variable (`let mut`, a function
parameter, or a captured mutable variable), stores that new array back into
`xs` — in every position, not only as a statement. So in a backtracking
search

```forge
fn solve(cols) {
    if len(cols) == 3 { return }
    for c in range(0, 3) {
        let next = push(cols, c)   // 2026: also changes `cols`
        solve(next)
    }
}
```

every iteration sees a longer `cols`. In edition 2027 `push(xs, v)`
returns a new array and never changes `xs` or any other variable, on both
engines. Unchanged in every edition:

- `xs.push(v)` (the method form) appends to a `let mut` variable in place
  and is the one way to mutate; it also returns the updated array.
- `xs = push(xs, v)` appends, and stays amortized O(1) on the VM (it
  compiles to the same in-place `PushLocal` as `xs.push(v)`).
- `pop(xs)` and `xs.pop()` remove the last element of a `let mut`
  variable (or parameter) and return it. A pure `pop` would return the last
  element and leave the array alone — that is `xs[len(xs) - 1]` — while
  silently turning every `while len(stack) > 0 { let top = pop(stack) ... }`
  into an endless loop, so `pop` keeps its 2026 meaning. On an immutable
  binding `pop(xs)` returns the last element without changing anything, as
  before.

**The error.** A statement whose whole value is a call of the builtin
`push` throws the new array away, so it does nothing in 2027. The type
checker rejects it before the program runs, in every mode:
**T0019** `the result of push() is discarded: push returns a new array and
does not change its argument (edition 2027)`, whose help names both
fixes: `xs = push(xs, value)` to keep the new array, or `xs.push(value)`
to append in place. It is reported for every statement whose value is
unused: any statement but the last one of a function, a lambda, a block
expression or the program (the REPL prints that one), including the last
statement of a loop body and of the branches of an `if`/`match`/`try`
statement whose own value is unused. It is not reported in edition 2026,
where the statement still appends. The checker cannot see every case: a
`push(xs, v)` used as a function's result or inside a larger expression
compiles and simply does not change `xs`.

**Migration.** `forge fix --edition 2027` rewrites a statement
`push(xs, v)` on a `let mut` variable or a parameter to
`xs = push(xs, v)`. It reports, and leaves alone, the uses whose meaning
changes and that it cannot rewrite: `push(xs, ...)` inside another
expression or as a function's result where `xs` is mutable (`let a =
push(cols, c)` also updated `cols` in 2026), and statements `push(xs, v)`
on an immutable `xs` (a no-op in both editions, rejected by T0019).
`xs = push(xs, v)` and `return push(param, v)` need no change.

## Migrating

```
forge fix --edition 2027                  # rewrite every .fg under the current directory
forge fix --edition 2027 src/ app.fg      # files or directories
forge fix --edition 2027 --diff .         # show a unified diff, write nothing
forge fix --edition 2027 --check .        # exit 1 if anything needs rewriting
forge fix --edition 2027 --set-edition .  # also set edition = "2027" in ./forge.toml
```

`forge fix` reads edition 2026 code and rewrites it token by token:
comments, blank lines and layout are kept, and running it again changes
nothing. It reports what it cannot rewrite mechanically, as
`file:line:col: ...`, and leaves it untouched (exit status 1): `safe { }`
used as a value, `check x is <anything but "not empty">`, removed forms
inside string interpolations, the builtins `sus`, `cook`, `yolo` and
`slay` (their output or error handling has no exact equivalent), and
`push(xs, ...)` uses whose 2026 meaning also updated `xs` (see
[`push` is a pure function](#push-is-a-pure-function); a statement
`push(xs, v)` on a mutable `xs` is rewritten to `xs = push(xs, v)`). Calls of a
removed builtin are only rewritten when the name is the builtin, not a user
definition of the same name.

Over this repository's own corpus (`examples/`, `tests/*.fg`,
`tests/parity/`), `tests/forge_fix.rs` checks that every fully rewritten
file parses under 2027, is a fixed point, and prints the same output under
2027 as the original under 2026.
