# Forge for Node.js: design note

Status: **plan only, not implemented.** The Python package
([`bindings/python`](../python)) ships first. This note records how the Node
package should mirror it, so the two stay one API in two languages.

## Goal

`npm install forge-lang` gives TypeScript/JavaScript agent hosts the same
deny-by-default sandbox as `forge_lang` in Python and `forge_lang::Sandbox` in
Rust: explicit capability grants, a wall-clock limit, an output cap,
cancellation and typed errors, all in-process, with no `forge` binary or
subprocess needed.

## Proposed API

```ts
import { Sandbox, ForgePermissionError, check } from "forge-lang";

const sb = new Sandbox({
  allow: ["env"],                  // Capability names, same as Python/CLI
  allowRead: ["./workspace"],
  allowWrite: ["./workspace/out"],
  allowNet: ["api.github.com"],
  maxTime: 5,                      // seconds
  maxOutput: 64_000,               // bytes
});

const { stdout } = await sb.run('say "hi"', { signal: AbortSignal.timeout(10_000) });
sb.runSync('say "hi"');            // blocking variant for scripts and tests
check("let y = (");                // Diagnostic[] — same as Python's check()
```

| Concept | Rust (`forge_lang`) | Python | Node |
|---|---|---|---|
| Sandbox config | builder methods | keyword args | options object (camelCase) |
| Run | `run_source` | `run()` (blocking, GIL released) | `run()` → `Promise<Result>`; `runSync()` |
| Cancellation | `CancelHandle` | `CancelToken` | standard `AbortSignal` |
| Errors | `SandboxError` variants | `ForgeError` subclasses | `ForgeError` subclasses with `kind`, `stdout`, `line`, `column`, `limit` |
| Check | `mcp::check_source` | `check()` | `check()` |

Error classes keep the Python names (`ForgeSyntaxError`,
`ForgePermissionError`, `ForgeRuntimeError`, `ForgeTimeoutError`,
`ForgeOutputLimitError`, `ForgeCancelledError`) and the same `kind` strings,
so agent code that switches on `err.kind` works across both hosts.

## Implementation plan (napi-rs)

1. **Crate.** `bindings/node/` with its own `Cargo.toml` (`crate-type =
   ["cdylib"]`, standalone `[workspace]`, `publish = false`), depending on
   `forge-lang` by path with `default-features = false` (no JIT; the
   sandbox runs on the interpreter) and the `postgres`/`mysql` features
   passed through, exactly like the Python crate. Dependencies: `napi` and
   `napi-derive` (v3), build with `@napi-rs/cli`.
2. **Never block the event loop.** `run()` returns a `napi::bindgen_prelude::
   AsyncTask` (or a `tokio`-free `ThreadsafeFunction` completion): the work
   runs on libuv's thread pool, which calls `Sandbox::run_source_cancellable`.
   That call already moves the program onto its own large-stack worker
   thread; the pool thread only lexes/parses, so run it on a dedicated
   thread with a large stack (as the Python binding does) rather than on
   libuv's small-stack pool thread directly.
3. **AbortSignal → CancelHandle.** On `run`, create a private `CancelHandle`;
   register an `abort` listener on the signal that calls `cancel()` on it.
   An already-aborted signal rejects immediately with `ForgeCancelledError`.
   Remove the listener when the task settles.
4. **Typed errors.** Define the error classes in a small JS shim
   (`index.js`) that wraps the native module, because napi-rs cannot
   declare JS subclasses of `Error` directly. The native side rejects with
   a plain object `{ kind, message, stdout, line, column, limit }`, and the
   shim maps `kind` to the class. `index.d.ts` is generated by napi-rs and
   then extended with the error classes by hand.
5. **Thread safety.** `Sandbox` is immutable after construction; each run
   clones the core `forge_lang::Sandbox`, so concurrent `run()` calls (and
   `worker_threads`) need no locking.
6. **Packaging.** napi-rs's standard prebuilt-binary layout: one npm package
   per target (`@forge-lang/linux-x64-gnu`, `-linux-arm64-gnu`,
   `-linux-x64-musl`, `-darwin-x64`, `-darwin-arm64`, `-win32-x64-msvc`) as
   `optionalDependencies` of `forge-lang`. Node-API v8 (Node 18+), so one
   build per target serves every Node version, like abi3 wheels for Python.
7. **CI.** `.github/workflows/node.yml`, modelled on `python.yml`: build each
   target with `napi build --release`, run the test suite (`node --test`)
   on Linux/macOS/Windows, and publish on `node-v*` tags with npm
   provenance (`npm publish --provenance`, OIDC), gated the same way PyPI
   publishing is.

## Tests to port

The Python suite (`bindings/python/tests/test_sandbox.py`) is the
checklist: happy path, every error kind with `stdout`/`line`/`limit`,
default-deny for each capability, scoped filesystem grants in a temp dir,
an infinite loop stopped by `maxTime`, the output cap, `AbortSignal`
cancellation, many concurrent `run()` calls (and policies not leaking
between them), the event loop staying responsive during a long run, and
the agent "code mode" handler pattern.

## Open questions

* Whether to expose a streaming `stdout` (callback per line) for long
  runs. The core `Sandbox` collects output into a buffer today; streaming
  would need a sink hook in `forge_lang::Sandbox` first, and Python would
  get it at the same time.
* Resource limits beyond time/output (instruction fuel, memory) are
  added to the core `Sandbox` first, then surface in both bindings as
  options plus their own error classes.
* Deno/Bun: Node-API works in both; verify before advertising.
